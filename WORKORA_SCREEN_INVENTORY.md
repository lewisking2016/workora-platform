# Workora Screen Inventory

This document lists the screens, sub-screens, and states Workora needs across web and mobile-adjacent product surfaces.

It is intentionally broad and should be treated as a living inventory.
If a surface exists in the product, should exist, or is needed to make the product feel complete, it belongs here.

## 1. Inventory Rules

- A screen is any distinct page, modal, drawer, full-screen flow, or error state that users can see.
- A screen family may contain many variants such as empty state, loading state, success state, error state, permission denied state, and retry state.
- Reusable UI controls such as buttons, cards, chips, and icons should still be tracked as interaction surfaces when they change behavior.
- Responsive variants count as separate delivery work when the layout or interaction changes materially on mobile, tablet, and desktop.
- The inventory includes current surfaces, missing surfaces, and future surfaces that the platform will need to feel complete.

## 28. Delivery Notes

- Every screen must have loading, empty, success, and error coverage where relevant.
- Every destructive action must have confirmation or undo behavior.
- Every upload flow must have progress, retry, and cancel states.
- Every auth flow must support session expiry and recovery.
- Every screen should emit analytics for page view, major actions, and failure states.
- Every screen should be responsive across small mobile, large mobile, tablet, and desktop sizes.

## 29. Definition of Done for the Screen Inventory

The screen inventory is complete when:
- every current route is documented
- every planned route is documented
- every modal, drawer, and full-screen state is documented
- every empty state and error state is documented
- the product team can use this file as the master checklist for delivery
